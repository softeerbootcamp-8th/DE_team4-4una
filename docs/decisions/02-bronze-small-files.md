# 02. Bronze 소파일을, 트리거 기준을 시간에서 오프셋으로 바꿔 해결한다

> 증상 대응을 명시적으로 기각하고 원인을 고친 사례입니다.

← [의사결정 목록](README.md)

## 트리거

Bronze 계층에 parquet 조각이 과도하게 쌓였습니다. 소파일은 이후 모든 읽기 단계의 성능을 갉아먹습니다.

## 관측된 사실

| 항목 | 측정값 |
| --- | --- |
| 5초 마이크로 배치 재생 시 1시간 Bronze 파일 수 | **3,545개** |
| 디스크 기준 행 크기 | **223 B/행** |
| 1시간 분량 (`data/mzlake`) | 12,058,018행 / 2.6 GB |

## 근본 원인

트리거 기준이 **시간**(5초)입니다. 유입량과 무관하게 5초마다 파일이 생성되므로, 파일 크기가 트래픽에 종속되어 통제되지 않습니다.

## 선택지

| 대안 | 장점 | 단점 | 기각 이유 |
| --- | --- | --- | --- |
| 트리거 간격을 늘린다 (5초 → 5분) | 변경이 가장 간단 | 여전히 시간 기준이라 트래픽에 따라 파일 크기가 요동친다 | **원인(시간 기준)을 그대로 둔 증상 대응** |
| 쓰기 후 별도 compaction만 수행 | 스트리밍 경로를 건드리지 않는다 | 소파일이 계속 생성되고, 정리되기 전까지 읽기 성능이 저하된다 | 생성 자체를 줄이는 편이 우선 |
| **오프셋 기준 배칭 + `coalesce`** | 파일 크기를 데이터량으로 직접 통제 | 저트래픽 시 쓰기가 멈출 위험 | **채택** (아래 보완과 함께) |

## 결정

- `minOffsetsPerTrigger = 600,000` — 측정된 223 B/행 기준 parquet 약 **128 MB**. 전체 partition 합계 기준이다.
- 쓰기 전 `coalesce`로 출력 파티션을 줄인다 (기본 1).
- `maxTriggerDelay = 5m` — 없으면 트래픽이 적을 때 스트림이 아무것도 쓰지 않고 멈춘다.

## 최적화 대상과 포기한 것

파일 크기와 읽기 효율을 얻는 대신 **적재 지연을 최대 5분까지** 허용했습니다. Bronze는 시간 단위 배치의 입력이므로 분 단위 지연이 하위 단계에 영향을 주지 않는다는 판단입니다.

## 검증 방법

- `STREAM_MIN_OFFSETS_PER_TRIGGER=600000`으로 재생 시 1시간 Bronze 파일 수가 **3,545개 → 20개 이하**, 평균 크기 약 128 MB
- 기존 checkpoint 재개 테스트 통과

## 결과

생성 단계에서 소파일이 줄었고, 그래도 남는 잔여 소파일은 **독립 compaction DAG**(`bronze_compaction`, 일간 `17 4 * * *`)로 정리합니다. 생성 억제와 사후 정리를 둘 다 두는 구조가 되었습니다.

## 재검토 조건

- 실시간성 요구가 생겨 5분 지연이 허용되지 않을 때
- 행 크기가 크게 바뀌어 600,000행이 128 MB에서 벗어날 때 (측정값 재산정 필요)
