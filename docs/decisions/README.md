## 기록 템플릿

```markdown
# <결정을 한 문장으로>

**트리거** — 무엇이 이 결정을 지금 강제했는가 (증상 / 요구 / 제약)

**관측된 사실** — 측정값·로그·재현 조건. 추측과 명확히 분리한다.

**근본 원인** — 증상이 아니라 원인. "왜"를 더 물을 수 없을 때까지.

**선택지**

| 대안 | 장점 | 단점 | 기각 이유 |
| --- | --- | --- | --- |

**결정** — 무엇을 하기로 했는가.

**최적화 대상과 포기한 것** — 무엇을 얻기 위해 무엇을 내놓았는가.

**검증 방법** — 이 결정이 옳았는지 판별할 측정 가능한 기준.

**결과** — 실제로 어떻게 됐는가. 예상과 달랐다면 그것까지.

**재검토 조건** — 어떤 사실이 나타나면 이 결정을 다시 열 것인가.

**근거** — 이슈 / PR / ADR / 코드 위치.
```

### 각 칸을 왜 두는가

일반적인 결정 기록은 **결정과 이유**만 남깁니다. 그것만으로는 몇 달 뒤에 읽는 사람이 "이 결정을 지금 바꿔도 되는가"를 판단할 수 없습니다. 아래 네 칸이 그 판단을 가능하게 합니다.

| 칸 | 없으면 생기는 문제 |
| --- | --- |
| **관측된 사실** | "느린 것 같다"로 시작한 결정과 "1시간에 3,545개 파일"로 시작한 결정은 신뢰도가 다르다. 수치가 없으면 나중에 개선 여부를 확인할 수 없다. |
| **근본 원인** | 증상에 대응하면 같은 문제가 다른 얼굴로 재발한다. "리소스 부족"과 "driver가 예산 전체를 소진하는 구조"는 완전히 다른 처방을 낳는다. |
| **포기한 것** | 트레이드오프를 적지 않으면 후임자가 "왜 이렇게 불편하게 해놨지"라며 이유 없이 되돌린다. |
| **재검토 조건** | 없으면 결정이 영구 제약처럼 굳는다. 전제가 깨졌는데도 아무도 다시 열지 않는다. |

### 지키는 규칙

- **측정 없이 성능 결정을 하지 않는다.** 완료 조건도 측정 가능한 형태로 쓴다 (예: "파일 수 3,545 → 20 이하").
- **증상과 원인을 같은 칸에 쓰지 않는다.** 로그·에러 메시지는 관측이고, 왜 그 로그가 나왔는지가 원인이다.
- **기각한 대안을 지우면 기록의 가치가 절반이 된다.** 왜 그것이 아닌지가 왜 이것인지보다 중요할 때가 많다.
- **되돌린 것도 결정이다.** 철회 사실과 이유를 남긴다.
- **범위 밖을 명시한다.** 다루지 않기로 한 것과 빠뜨린 것은 다르다.
