# 07. 중간 산출물을 S3에 쓰지 않고 인메모리로 전달한다

> 무엇을 포기했는지, 그 포기가 왜 감당 가능한지 함께 적은 사례입니다.

← [의사결정 목록](README.md)

## 트리거

정제(T1) 결과 `processed_sensor_event`를 S3에 쓰고, 시간별 특징 산출(T2)이 그것을 다시 읽는 구조였습니다.

## 근본 원인

T2가 **같은 실행 흐름에서 즉시 소비**하는 데이터에 영속 경계를 둔 것입니다. 그 결과:

- 매시간 쓰기와 재읽기 I/O가 발생한다
- 임시 데이터의 저장 수명과 `event_hour` 파티션을 관리해야 한다

## 선택지

| 대안 | 장점 | 단점 | 기각 이유 |
| --- | --- | --- | --- |
| 기존 S3 저장 유지 | T1·T2를 독립적으로 재실행 가능, 중간 결과 조사가 쉽다 | 매시간 쓰기·재읽기 I/O, 임시 데이터 수명·파티션 관리 | T2가 같은 실행 흐름에서 즉시 소비하므로 영속 경계의 비용이 이점보다 크다 |
| T2가 Bronze를 직접 읽고 클렌징까지 수행 | T2 단독 실행 형태를 유지할 수 있다 | T1 책임이 T2에 중복되고 quarantine 처리·규칙 적용 지점이 불명확해진다 | 클렌징 책임을 T1에 유지해야 데이터 품질 경계가 명확하다 |
| 별도 상위 coordinator job 추가 | 실행 흐름의 이름이 명확해진다 | 새 진입점과 배포·테스트 표면이 추가된다 | 기존 cleansing job이 같은 Spark 세션의 진입점을 맡는 것으로 충분하다 |
| **같은 Spark 세션에서 DataFrame 전달** | I/O와 관리 비용 제거 | T2 단독 재시작 불가 | **채택** |

## 결정

같은 Spark 세션 안에서 DataFrame으로 전달합니다. 중간 Parquet 쓰기·읽기와 `event_hour` 파티션 관리가 제거됩니다.

`event_date`와 `event_hour`는 T1→T2 인메모리 계약에 포함하지 않습니다. T2 출력 경로의 날짜·시간은 실행 인자인 `target_hour`에서 결정합니다.

## 최적화 대상과 포기한 것

I/O와 관리 비용을 줄이는 대신 **T2만 독립적으로 재시작하는 능력을 포기**했습니다. 실패하면 불변 Bronze부터 해당 시간을 다시 처리합니다.

**이 포기가 감당 가능한 이유** — Bronze가 불변(append-only)이므로 재처리가 항상 같은 결과를 냅니다. 중간 결과를 보존하는 가치는 "재현할 수 없을 때" 큰데, 여기서는 재현이 보장됩니다.

## 부수적으로 필요해진 처리

T2의 lookback/lookahead를 충족하기 위해, T1은 대상 시간뿐 아니라 **경계와 겹치는 인접 Bronze 시간도 함께 클렌징**합니다. 시간별 중복 제거 의미를 유지하면서, quarantine 교체는 대상 시간에만 수행합니다.

## 재검토 조건

T2 연산이 무거워져 재실행 비용이 커지면 중간 체크포인트를 다시 고려해야 합니다.
